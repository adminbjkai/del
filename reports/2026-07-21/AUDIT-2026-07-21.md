# DEL Host Full Audit Report — bjkai-2tb-ubuntu

Date: 2026-07-21
Scope: Full read-only audit across nginx, Docker, systemd, firewall/ports, filesystem/git, and the DEL codebase itself, run as 6 parallel audit lanes and synthesized here. Confirms the state of the server after this session's deletion of BoxBox, filebrowser, rustpad, rustdesk, and xtrdash (+ xtr-dashboard.service).

---

## Executive Summary

The host is fundamentally healthy: `nginx -t` passes cleanly, there are **0 port collisions**, **0 duplicate domains**, all SSL certs are valid with 55+ days of runway, and IPv6 is confirmed **not** an exposure gap despite ufw's `IPV6=no` setting (Tailscale's own ip6tables rules cover it). Of 124 enabled nginx sites, 121 routes are live; 8 are dead (502).

The five apps deleted this session are **cleanly gone** everywhere except one place: nginx still has an enabled, dead site for **boxbox.bjk.ai** (proxying to a port nothing listens on). No systemd, Docker, or filesystem leftovers exist for any of the five.

Beyond the cleanup-verification scope, the audit surfaced a few things worth the owner's attention:

- **High severity (2):** the **kanbu** app's API backend has been crash-looping for 500+ restarts because of a Docker Compose project-name collision with karakeep (both directories are named `docker`), and **semalist.bjk.ai** is running live but has silently fallen out of PM2's persisted process list — a reboot right now would permanently lose it with no supervisor to bring it back.
- **Medium severity (6):** an orphaned nginx site (boxbox), a degraded-but-"healthy"-looking blinko stack (its Postgres container has been exited 31 hours with a restart-policy mismatch), a crashed-since-2+-weeks `shows.service` that's still marked enabled, a stray unsupervised Node process quietly keeping htmls.bjk.ai alive with zero crash recovery, a Flussonic media server reachable both through nginx and directly on a wide-open port (TLS/vhost bypass), and a DEL-codebase bug where the miscwork.html inventory export template was edited but the file that publishes it was never rebuilt (so the live page is stale).
- **Low/info severity (rest):** stale ufw rules, a stale nginx.conf.bak, disk-hygiene items (a 7.5GB stale backup buried in a dead app directory, ~1.9GB of loose zips at `/apps` root), 23 on-disk app directories with no running containers, inconsistent firewall hardening (Samba/NoMachine open to Anywhere unlike SSH), and a data-integrity bug in DEL's own systemd parser.

Nothing found requires emergency action. The two high-severity items (kanbu DB, semalist PM2 persistence) are the most consequential because they represent silent, ongoing failures (kanbu: broken since deployment; semalist: a ticking time bomb for the next reboot).

## 4. Docker

### No conflicts confirmed (healthy)
- Zero leftovers (containers/images/volumes/networks) for any of the 5 deleted apps.
- 0 live host-port collisions (18 ports are reused across 168 on-disk compose files, but all overlaps are in undeployed dev/test variants of cloned upstream repos — verified inert via `docker ps` + `ss -ltnp`).
- The 3 `<none>:<none>` "dangling" images are all actively referenced by running containers (e.g. shared Postgres base layers) — not real reclaimable space.
- 162 of 163 containers have a working restart policy and are `Up`.

### High: kanbu API permanently crash-looping
`docker-api-1` (kanbu's backend) has **RestartCount = 518** and climbing, looping forever on "Could not connect to database after 30 attempts." Root cause: `/apps/kanbu/docker` and `/apps/karakeep/docker` are both literally named `docker`, so `docker compose` defaulted both to the same project name `docker`, merging kanbu's and karakeep's compose files into one project. Only `docker-web-1`, `docker-api-1` (kanbu), `docker-meilisearch-1`, `docker-chrome-1` (karakeep) exist under that project — **no `docker-postgres-1` was ever created**, so kanbu-api's `DATABASE_URL=postgresql://...@postgres:5432/kanbu` can never resolve. The kanbu web frontend (nginx serving static files) loads fine, masking that every backend call is broken. This has likely been broken since kanbu was first deployed.

Side effect (low): `docker-meilisearch-1` and `docker-chrome-1` are pure duplicates of the already-healthy `karakeep-meilisearch-1`/`karakeep-chrome-1` (project `karakeep`, correctly deployed, `Up 31 hours`) — wasted idle containers from the same collision.

### Medium: blinko-postgres exited, restart policy drifted from compose file
`blinko-postgres` is `Exited (0) 31 hours ago` (clean shutdown, not a crash) and has not restarted despite `/apps/blinko/docker-compose.deploy.yml` declaring `restart: always`. `docker inspect` shows the *running* container's actual `RestartPolicy.Name = "no"` — the live container's policy has drifted from what the compose file says, so Docker never attempted to bring it back. `blinko-website` reports "healthy," but its healthcheck only probes the web process (`wget --spider` on its own port), not the database it depends on — so the "healthy" status is misleading. Any DB-backed action in blinko (login, saving notes) is at risk of failing right now.

### Info: 17 orphan volumes, 23 down app directories, 2 wide-bind containers
- 17 Docker volumes have zero container references. Most are explained: `docmost_postgres_data` is an intentional pre-migration rollback backup (documented in its own compose file); `docker_data`/`docker_kanbu-db-data` are byproducts of the kanbu/karakeep collision above; the rest belong to the 23 stopped app directories below. `automation-stack_metabase_data` is the one that looks like an actual gap — the compose file defines a `metabase` service but no such container exists at all.
- 23 `/apps` directories have on-disk compose files with zero running containers (bjkai_shorturl_by_claude, boxy, Cap, cap5, cap_v2, dockhand, fizzy, flagsmith, gateway, kestra, KittyClaw, many-notes, midarr-server, monitoring, netdata, nginx-ui, notecapai, notes-dashboard, poco-claw, showdoc, ViniPlay, wanwu, zed) — general hygiene, none tied to this session's deletions.
- `anisette` (0.0.0.0:6969) and `nextcloud-aio-talk` (0.0.0.0:3478) are the only 2 containers (of ~163) that bind all interfaces instead of loopback — plausibly required by function (client discovery / WebRTC TURN), not flagged as urgent.

## 5. Systemd

### No conflicts confirmed (healthy)
- `systemctl --failed`: none.
- No unit's `ExecStart` binary/script is missing (all ~50 custom units checked).
- No orphan unit files for any of the 5 deleted apps — `xtr.service` confirmed as a separate, legitimate, still-needed unit.

### Medium: shows.service enabled but dead 2+ weeks
See §3 above — `Restart=on-failure` doesn't cover a clean SIGTERM, so once something killed it on 2026-07-04, it never came back despite being enabled for boot.

### Medium: htmls-webapp.service disabled; site kept alive only by an unsupervised stray process
`htmls-webapp.service` is `disabled`/inactive, yet `htmls.bjk.ai` is live — served by a stray, manually-started `node server.js` (PID 3584797, started 2026-06-16, parent PID 1, not under systemd/pm2/docker) that happens to bind the same port (8195) the disabled unit would use. No crash recovery exists for this process; a crash or reboot takes the site down with nothing to restart it, even though the correct systemd unit to do so already exists on disk, just disabled.

### High: pm2-root.service / semalist.bjk.ai — invisible to PM2's own bookkeeping, reboot-fragile
`pm2-root.service` (`ExecStart=pm2 resurrect`) is active and genuinely supervises semalist.bjk.ai (PID 2199, port 3020, confirmed live). But `pm2 list`/`pm2 jlist` against that same `PM2_HOME=/root/.pm2` return an **empty table** — `/root/.pm2/dump.pm2` is a literal `[]` (written 2026-07-08), while its own `.bak` from the same date still lists semalist. This means:
1. Any tool enumerating pm2 apps the standard way (`pm2 list`) sees **zero** apps and misses semalist entirely — this is the direct cause of the DEL-codebase app-detection gap (§7 below).
2. **Reboot risk is real, not hypothetical**: `pm2-root.service` starts via `pm2 resurrect`, which reads the now-empty `dump.pm2`. If the host reboots today, the daemon comes back with zero apps and semalist.bjk.ai does **not** restart — there is no other supervisor for it.

### Info
- `/apps/m3try/deploy/restream.service` exists on disk but was never installed to `/etc/systemd/system` — deploy artifact, not a bug.
- `trflix.service`, `notecapai-doc-worker`/`-image-daemon` (disabled) are consistent explanations for those already-known dead routes, not new discrepancies.
- `urlshortener*`, `nginx-ui.service`, `neoclaw-forward.service` (disabled, no nginx site pointing at them) look intentionally retired.

## 6. Firewall / Ports

### No conflicts confirmed (healthy)
- ufw active, default-deny incoming, logging on.
- IPv6 verified **not** an exposure gap: `ip6tables` (Tailscale-managed) has `INPUT` policy `DROP` with only `lo` and Tailscale's chain accepting; no public IPv6 address on the host.
- None of the 8 dead nginx routes (§3) have a corresponding ufw rule either — dead apps aren't compounding into an extra firewall hole.
- SSH is correctly locked to 2 specific source IPs.
- 18 host-port reuses across 168 compose files are all in undeployed dev/test variants — zero live collisions.

### Medium: Flussonic reachable both via nginx and directly on the open port
Port 8050 (Flussonic media server, backing `flussonic.bjk.ai`) is `ufw ALLOW Anywhere` and listens on `0.0.0.0`, so it's reachable both through nginx's TLS-fronted vhost and directly over plain HTTP on `:8050` — a TLS/vhost bypass.

### Medium: Samba and NoMachine open to Anywhere, unlike SSH
`Samba` (139/445) and NoMachine (`4000` tcp+udp) are `ufw ALLOW Anywhere` with no source-IP restriction — inconsistent with SSH, which is already IP-locked to 2 addresses on this same host. NoMachine in particular has a history of CVEs.

### Low: 25 stale ufw rules with no listener anywhere
Ports 55, 3001, 3004, 3052, 5000, 5005–5008, 5174, 5555, 7005, 7071, 8097, 8098, 8100, 8101, 8123, 8443, 8800, 8922, 8923, 9001, 9090, 9100 have `ALLOW` rules but nothing listens on any of them, loopback or otherwise. None trace to the 5 deleted apps. Standing invitations for anything that binds those ports in future to become instantly reachable.

### Info
- AionUi's Electron process has an unexplained second listener on `*:3000` (ufw-restricted to 1 IP) beyond its documented loopback `3180` — looks like an electron-forge dev-server default, worth a confirmation with the owner.
- 2 containers bind wide (see Docker §4) — not currently internet-exposed (NAT/ufw), but reachable from LAN + full Tailscale tailnet.

## 8. DEL Codebase (miscwork.html / correlate.py / systemd_src.py)

### High: miscwork.html inventory export is stale — template edited, publish step never run
`del-inventory.template.html` (the true editable source, containing the `__INVENTORY_JSON__` placeholder) was edited this session (cropping-fix CSS, de-pilled chips, new `domainLinkRenderer()` clickable-domain feature) **after** `del-inventory.html`/`miscwork.html` were last built from it. No script in `/apps/del/miscwork/` (`extract.py`, `build_workbook.py`, `inline_build.py`) performs the template→HTML substitution — it was apparently done by hand once and never captured as a script. The live page at `https://del.bjk.ai/miscwork.html` (and `/inventory`) is confirmed (via diff) to be missing all three fixes right now.

### High: pm2-managed apps are structurally invisible to DEL's Apps list
Root-caused in `correlate.py`: Step 6b only seeds an app from a custom systemd unit when that unit's `WorkingDirectory`/`ExecStart` resolves under a scan root. `pm2-root.service`'s real `ExecStart` (`pm2 resurrect`) never does, so it's never seeded as an app, and Step 9b (port/process attribution) only attaches to units already seeded — so semalist.bjk.ai's port and process are permanently unattributed. This is a documented, known-but-unfixed gap: `docs/SYSTEM-STATE.md` item #5 already calls out "semalist, trp, 17imgshare — live but untracked" and recommends adding manifests; `/apps/del/manifests/` still contains only `del.yaml`, so the fix was never applied.

### Medium: systemd_src.py's batched systemctl parser misattributes ExecStart for SysV-shimmed units
Reproduced directly: in a 50-unit batched `systemctl show` call, each SysV-init-shimmed unit's `ExecStart` property (a structured, multi-line value) is shifted one unit-block down from where the parser expects it, purely because of `Id=`-only record delimiting. Confirmed live: DB stores `pm2-root.service`'s `exec_start` as `/etc/init.d/pmcd start-systemd` (that's actually `pmcd.service`'s value) even though live `systemctl show` returns the correct value. Currently harmless on this host (none of the shifted values happen to point at a real scan-root path) but is a genuine, reproducible data-integrity bug.

### Low: OPERATIONS.md underspecifies the export chain
Doesn't name the missing template-render step or state that the template file, not `del-inventory.html`, is the true editable source — the direct documentation counterpart of the High finding above.
