An **orphan candidate** is a resource that showed up in the latest scan but which DEL
could not tie to a **current, confident owner**. The **Orphans** page collects them,
grouped by resource type.

## What counts as "no owner"

A resource is listed when **no** association on it satisfies all three of:

1. the association is not excluded;
2. its confidence is **at least 60** (`probable` or better); and
3. the owning application is itself present in the latest completed scan.

Conditions 2 and 3 are not incidental — each closes a hole where a resource that
genuinely needed attention was hidden:

- **Without "the owner still exists"**, a resource whose only owner was an
  application removed several scans ago stayed permanently invisible on the page
  whose entire purpose is to surface exactly that leftover. (The scanner now also
  purges associations belonging to applications that are no longer in the scan, so
  those ghost owners disappear at the source too.)
- **Without the confidence floor**, a weak sub-60 name-similarity guess was enough
  to hide a resource while being far too weak to make it removable through any
  application — a dead zone where it was neither actionable here nor cleanable
  there.

A consequence worth knowing: a resource whose only owner is a `probable` (60–79)
association will **not** appear here, even though `probable` associations are never
included in a removal plan either. Those show up in the plan's *Preserved* list
instead — see [Understanding Confidence](/guides/confidence).

## How to reason about an orphan

An orphan is not automatically junk. Before acting on one, work out which it is:

- **Genuinely abandoned** — a leftover volume from an app you already removed, a
  dangling image, a stopped container with no owner. These are usually safe to clean
  up.
- **Shared infrastructure** — a network, volume, or directory used by several things
  that DEL couldn't confidently attribute to one app. Removing it could break
  something. Nested Compose projects inside another app's tree remain blocked;
  definitions declaring bind mounts or named volumes are treated as data-risk,
  not merely config-risk. Bare signal-less directories remain unassociated rather
  than receiving a weak name-only owner.
- **Simply un-correlated** — a resource DEL failed to link because of a naming or
  path mismatch. The fix is to add a [manifest](/reference/architecture) entry so the
  next scan attributes it correctly, rather than treating it as an orphan.

The dashboard's **Orphan candidates** stat card links straight here, and each group
heading links to that type's tab in [Resources](/guides/browsing) for the full
per-type detail (mountpoints, sizes, containers using a volume, and so on).

### Noise reduction

Ports and processes that DEL can trace back to an owning docker container or
systemd unit (via a cgroup match) are attributed to that container's/unit's
application automatically and never appear here as orphans — they're owned
infrastructure, not debris. Only ports/processes DEL genuinely couldn't attribute
to anything show up on this page.

For a listener under a systemd user manager, the owning unit is the innermost
service in its cgroup path: `openclaw-gateway.service` running under
`user@1000.service` is reported as `openclaw-gateway.service`. The user manager
is used only when nothing deeper is present. System units are read as before. If that unit is a vendor/package unit listed in
the same scan (unit file under `/lib/systemd` or `/usr/lib/systemd`, for example
`flussonic.service` from the `flussonic` package), the port is shown as
**System**, the same bucket as the unit row. DEL only removes units under
`/etc/systemd/system`, so the package manager owns these. Only an exact cgroup
match counts, and `user@*.service` never does.

When the same process binds a port on both IPv4 and IPv6, the second socket is
**Expected** and points to the first. A Git repository row inside a candidate
directory is also **Expected**, because you review the directory instead. An
enabled site with no owner stays **Actionable**, and its reason names each
loopback proxy target and the unit that owns that listener, for example
*"proxies to 127.0.0.1:18789 (openclaw-gateway.service)"*.

An unused image is also checked against every discovered compose file: if a
`docker-compose.yml` still declares an image that no running container currently
uses, its reason reads *"unused, but referenced by compose project &lt;name&gt;
(not currently running)"* rather than the generic *"not used by any container"* —
a hint that starting that compose project would bring it back into use, rather
than it being pure debris. A detached named volume with only an old Compose
project label is retained as a low-confidence historical association, so it
remains visible here for review instead of being mistaken for current app-owned
data. Nginx sites-available copies that aren't linked into sites-enabled
(stale/backup files) read *"config file not enabled (stale copy/backup)"*;
enabled sites DEL attributes through the live published port when possible and
reports whether the application runtime is confirmed running.

## Acting on an orphan

Because there are no delete buttons on this page, you act on orphans one of two ways:

1. **Attribute it, then remove via its app** — add or correct a
   [manifest](/reference/architecture) so the resource is associated with the right
   application, rescan, and remove it as part of that app through the normal
   [removal flow](/guides/removing-an-application).
2. **Clean it up outside DEL** — for a truly standalone leftover (e.g. a dangling
   image or an unused volume with no app), remove it directly with the appropriate
   host command. DEL's discipline of "never delete what you can't attribute" is why
   this is left to you deliberately.

<Callout intent="warning">
  Investigate before you act. A volume with no *containers using* it may still be a
  periodic-job's data store, and a network with no attachments may be created on
  demand. When in doubt, back it up first — see [Backups & Restore](/guides/backups).
</Callout>
